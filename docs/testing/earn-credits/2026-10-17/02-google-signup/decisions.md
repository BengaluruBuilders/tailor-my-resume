## 1. Same-UID recovery uses durable transition evidence

**Accepted rule.** Separate the short-lived bearer intent from a durable prelink observation. Preparation requires an authenticated guest, authoritative Firebase lookup confirming the same UID/account incarnation has no Google provider, no recorded prior Google activation, and an eligible known-guest classification. Persist app/environment, UID, trusted Firebase creation time, attempt ID, server preparation time, classification provenance, and a finite recovery expiry. Hash the bearer secret separately. Token provider flags alone do not prove current provider absence: an old anonymous token can outlive a link.

After linking, require a refreshed, verified Google-authenticated token and authoritative lookup of `google.com` provider subject for that UID. A missing or expired bearer secret does **not** defeat same-UID recovery while the durable prelink fact remains valid. Same UID plus matching trusted Firebase creation time, eligible prelink fact, current Google provider, and no prior incompatible activation is sufficient to recover that transition. Check grant/subject uniqueness, policy/evidence/capacity and deletion guards before any new award. A fresh action challenge can replace expired Integrity evidence without replacing the business attempt or its eligibility anchor.

Record first Google observation/eligibility separately from grant commitment. A provable eligible transition can remain pending when policy/evidence/capacity is temporarily unavailable; retry resumes it rather than treating the user as an unrelated returning account. Once committed, recover its original receipt before fresh admission/evidence checks, after authentication/live-account checks. A new request ID or policy revision never creates another entitlement. A historical/returning activation has an immutable non-new classification; token refresh cannot convert it to pending-new.

No prelink proof and no eligible authoritative direct-new classification means **no new bonus**. Return an explicit conservative ineligible/recovery-expired reason while preserving account access, existing balance and work. Do not guess from email, last sign-in, token `auth_time`, or backend row creation. If only the short secret expired, use the durable proof; if the durable proof itself expired or was erased, do not fabricate it. This is a bounded recovery guarantee, not guaranteed recovery after arbitrary delay.

The UID's authoritative creation time is an incarnation check, not an anonymous-to-Google event timestamp. A mismatch rejects stale intent/activation reuse. Erasure invalidates all attributable prelink/activation state. Recreating a Firebase account does not inherit an old proof, even if an administrator reuses the UID. Ordinary Firebase deletion/recreation usually has a new UID and remains subject to the retention limits in decision 3.

**Required cases.** Unused trial `2 → 7`; one spent credit `1 → 6`; link succeeds/app dies before response; local secret missing; secret expired/durable fact valid; challenge expired/fresh challenge same attempt; lost successful response after policy pause; two devices/two request IDs; recorded returning account; prelaunch/ambiguous old account; durable fact expiry; deletion during finalize; same UID with changed Firebase creation time. Successful recovery adds exactly one +5 and no extra base grant.

**Basis.** Firebase documents anonymous-account linking and credential conflicts, but its Admin `UserMetadata` lists creation, latest sign-in and latest refresh timestamps; `UserInfo` lists provider ID/subject without a provider-link timestamp. Absence of a link timestamp is an inference from those documented interfaces, not proof of an undocumented timestamp. See [Admin metadata](https://firebase.google.com/docs/reference/admin/node/firebase-admin.auth.usermetadata), [provider identity](https://firebase.google.com/docs/reference/admin/node/firebase-admin.auth.userinfo), [anonymous linking](https://firebase.google.com/docs/auth/android/anonymous-auth), and [conflicts](https://firebase.google.com/docs/auth/android/account-linking). The plans explicitly require crash recovery and prohibit classifying ambiguous old identities as new.

## 2. Freeze a conservative eligibility anchor per real preparation attempt

**Accepted rule.** Store `firstGoogleObservedAt` as the first server verification of Google identity. It is a server fact, not a claim about when Firebase linked the provider. For a known guest, use the server preparation time of the qualifying prelink attempt as `eligibilityAnchorAt`; for an eligible direct-new Google identity, use authoritative Firebase account creation time. Persist the anchor, provenance, selected referral-window duration and deadline once Google is observed/classified. Do not use completion time, token refresh, policy publication, or latest sign-in to refresh it.

Unused attempts are replaceable. A guest may cancel a Google prompt, use the app for weeks, then prepare again. A new preparation may supersede the old unused attempt **only** after a fresh authenticated guest request and authoritative same-incarnation lookup confirms Google is still absent and no durable Google observation/activation exists. A client cancellation flag or expired secret alone is insufficient. Do not permanently anchor a person to their earliest cancelled Google prompt. Keep one current unused observation per account and supersede its previous secret; bound replay records separately.

If that lookup discovers Google, freeze/reconcile the already prepared transition rather than issuing a fresh preparation/clock. Google observation and preparation replacement use the same user lock and immutable state check; a concurrent finalization cannot be overwritten. Provider lookups occur outside the transaction with bounded freshness/timeout, and the transaction rechecks state. Tests must cover races and reject stale snapshots that would replace an already observed activation.

For link-then-crash recovery after secret expiry, retain the original qualifying preparation anchor. Delaying finalization may consume or exhaust referral time; it cannot create a fresh deadline. A cancelled attempt followed by a genuinely provider-absent new preparation receives that new attempt's anchor. The anchor is a conservative lower bound on the subsequent link event, **not** an actual provider-link timestamp. The consequence is explicit: an unusually long preparation-to-link delay can shorten the referral opportunity. Without another trustworthy provider event, exact link-time fairness and prevention of arbitrary delayed-finalization refresh cannot both be promised.

The +5 signup entitlement is separate from the referral attachment window: an expired referral deadline alone must not erase an otherwise provable pending signup bonus. Referral admission still needs its own configured policy. A completed attachment replays after the deadline without a second reward. No source here approves a live 24-hour window, launch cutoff, or retroactive campaign for existing users. Missing classification/cutoff policy must fail new rewards safely and never rewrite the first observed dates later.

**Required cases.** Guest creation long before linking; cancelled first attempt then new provider-absent attempt weeks later; expired attempt renewed while still genuinely guest; linked account trying to prepare with stale anonymous token; concurrent renewal/finalization; link before expiry and recovery after expiry; delayed finalize after referral deadline (signup may still succeed); direct signup delaying its first API call; retries across policy/window changes; committed attachment replay after expiry. Assert anchors never move after Google observation.

## 3. Separate live-account business facts from finite identity aliases

**Accepted baseline.** Keep the minimal activation classification, immutable dates, own grant/entitlement marker and opaque receipt for the living account until erasure; these are necessary account/ledger business state and survive sign-out/device changes. They contain no raw email or raw Google subject. Expiring or rotating an abuse alias does not delete a live account's granted/previously-activated marker or make it new again.

Store the verified Google subject only as a purpose-specific HMAC alias with app, Firebase project/environment, purpose, key version, first observation and explicit finite `expiresAt`. Use a dedicated Google-signup purpose/key domain, separate from Android-ID continuity, request fingerprints, other apps and environments. Compute raw subject transiently from the authoritative provider record; never persist/log it or use email as its replacement. Do not embed the HMAC or deleted UID in a supposedly opaque surviving grant/capacity source. Keep account-lifetime uniqueness by account entitlement; keep cross-UID subject suppression in the expiring alias table.

Within that configured alias lifetime, subject suppression prevents easy unlink/new-UID regrant, with stable entitlement uniqueness independent of request/policy revisions. Alias expiry is measured from its original observation/claim and is not silently extended by every login. If policy deliberately renews an alias, that must have an explicit disclosed finite lifecycle; it is not this baseline. After expiry, own live-account markers still prevent same-account regrant, but cross-UID suppression cannot be promised. No invasive fingerprint substitutes for the expired alias.

**Post-deletion retention is zero in this baseline.** `DELETE /v1/me` erases aliases, activation, pending proofs, operations/challenges and attributable counters through existing guarded/retryable cleanup. Preserve only nonidentifying campaign consumed totals and the existing bounded deletion tombstone. This adopts no exception to constitution rule 9. A later deletion-resistant alias would require a separately reviewed bounded exception, disclosure, expiry job and access/export treatment. Deletion/recreation may therefore qualify again; do not advertise permanent per-human/per-Google prevention. Campaign capacity bounds exposure and does not reopen on deletion.

Rotation compares candidate aliases under every still-required retained key version, then locks those alias keys in one deterministic order with the account/grant transaction. New aliases must not reset original expiry or create another entitlement. Retain key overlap until existing aliases expire or use an explicitly designed migration; missing required key/version disables new admission rather than treating everyone as unseen. Once the retained window ends and its rows are purged, erase unneeded old keys through the operational secret process. No secret is printed/exported by this report.

Export own activation/classification/eligibility dates and grant receipts/ledger, plus understandable evidence categories, purpose and expiry where relevant. Do not export another account's identity, raw subject/HMAC/secret, Integrity token or internal risk parameters. User erasure covers the identifiable rows, including on partial failure/retry; backup restoration follows existing deletion reconciliation. These implementation/export choices do not substitute for approval of final production disclosures.

**Fixture values only.** Secret TTL 5 minutes; unobserved prelink recovery evidence/replay cache 30 days; provider alias 180 days; referral window 24 hours. All are explicit synthetic policy values, not approved staging/production collection or admission defaults. Live-account entitlement/activation facts last only while that account exists; observed pending activation retains its minimal business fact while the account lives, rather than expiring into a fresh eligibility classification. No active policy may rely on an unavailable or erased alias for a stronger guarantee.

**Required cases.** Sign-out/new device; same UID after alias expiry; subject reuse across UIDs within retention; alias expiry then new UID (documented limitation); two key versions/rolling instances; missing retained key; deletion at each cleanup step; expired proof never resurrected; deletion/recreation; aggregate consumption unchanged after erasure; export contains own dates/receipts but no hashes, secrets or counterpart identifiers.

## 5. Final clarification: positive direct signup and immutable replay

### Sufficient trusted direct-new classification

Define the qualifying event as a **new Firebase account in this app/environment**, not creation of the person's Google/Gmail account and not proof the Firebase account was never anonymous. A brief unobserved anonymous phase within the configured new-account interval is acceptable. Requiring historical never-anonymous evidence from current Admin metadata would make ordinary direct signup unimplementable and is rejected.

A positive `DIRECT_GOOGLE` classification requires all of: authoritative Firebase creation at/after the configured eligibility cutoff; first trusted Google observation within an explicitly configured maximum age from that creation (plus bounded clock skew); current verified Google token and matching authoritative same-project Google provider subject; no incompatible durable prior activation/legacy/conflict history; and no retained subject claim/grant that already consumes signup eligibility. Ordinary eligible direct signup therefore has a real positive +2/+5 path. Current Google-only provider metadata may be required by the app policy, but it does not prove historical provider exclusivity. Client `isNewUser`, email, backend row creation and latest sign-in are not sufficient evidence.

Known durable prelink provenance takes the guest-link path; it cannot be ignored to bypass a stale/expired/incompatible guest transition. Google creation before cutoff, first observation outside the new-account interval without valid guest-link proof, incompatible historical records and insufficient/contradictory metadata stay existing/ambiguous and closed. An absent provider lookup is a retryable outage, not proof of newness. A prior committed own grant is receipt recovery before classification/admission. The direct eligibility anchor remains trusted Firebase creation, so delaying observation never resets a window.

The accepted limitation is explicit: this recognizes new app accounts, including a short unobserved anonymous-to-Google conversion, rather than proving the provider's exact first link event. It does not prove a unique person, prevent all abandoned-account farming, or defeat deletion/recreation beyond retained alias policy. Finite subject suppression, unchanged protected base allocation and configured capacity remain required. Deterministic fixture maximum direct-new observation age: 10 minutes; live cutoff/age/skew are unset activation inputs. Tests must prove plain direct new account and brief anonymous phase both succeed, while old/out-of-window/incompatible histories cannot enter this path.

### Committed response and missing-base retry

For a committed `(actor, GOOGLE_ACTIVATION, requestId)`, return its **immutable outcome snapshot**: signup/base statuses and original receipt references/amounts/revisions, with the **current** wallet. Same key/different stable business payload conflicts. Do not silently reevaluate a previously denied/unavailable/not-attempted base on that committed key. Temporary base unavailability is final only for that attempt, not a permanently forfeited entitlement. A lost response must replay the original result even after policy pause, provider outage, attestation expiry or spending. Exact per-attempt snapshot/fingerprint replay lasts while its finite operation record exists; after cache expiry, durable account/grant facts still reconcile original receipts/current wallet without duplicate credit, but must not be presented as an exact reconstruction of an erased denial snapshot. Keep a constant-sized original successful signup/base operation fingerprint/snapshot with its durable activation/grant fact if exact successful-operation recovery is required beyond cache expiry. Do not retain an unbounded history of failed attempts. Snapshot replay and receipt reconciliation must remain distinguishable.

To retry an uncommitted base after +5 committed, allow an **explicit new request ID and fresh combined-action challenge** under the same durable eligible `DIRECT_GOOGLE` fact. Preserve the original chosen base continuity fingerprint once a base was requested; fresh evidence or policy does not mutate that identity signal. If the original signup did not request base, a new explicit base request may supply its first continuity signal. The signup subdecision recovers its existing receipt and cannot issue another +5. Evaluate current eligibility/security/policy/capacity only for the new base subattempt. Its pair binds `[original committed signup revision, current requested base revision]`; an old/paused/new signup campaign cannot block an otherwise eligible uncommitted base. Stable `guest-trial` account/allocation uniqueness still governs. A permanent account-level legacy/ineligible base classification remains closed; `GUEST_LINK` never gets a refill. A still-allocated signal still denies under its normal policy.

Recovery is symmetric: after a base-first +2 outcome with signup temporarily unavailable, an explicit new-key/challenge signup attempt can add the eligible +5 later. Return the original base receipt; its original revision satisfies the committed-base precondition even if the current base campaign is paused, changed, expired or absent. Bind `[current requested signup revision, original committed base revision]`. Never repeat the base or re-evaluate its admitted continuity to recover its receipt. The immutable direct-new classification/anchor and pending signup fact survive the partial outcome. Same-key replay remains the original snapshot, not a silently upgraded +7 response. Both directions preserve prior spending and apply only the missing eligible grant.

When both grants already exist, or no requested action remains uncommitted, reconcile the receipts/current wallet without new evidence/provider calls. When a new subgrant remains, authenticate/live-check and recover existing receipts first, then verify authoritative current identity/incarnation and fresh evidence for that new work. SQL failure rolls back all **new** writes; it never rolls back the historical signup grant. The frontend must explicitly start the new base attempt rather than reusing a committed key expecting a different result. Do not treat a temporary base sub-outcome as an unavailable whole activation or erase an otherwise eligible +5.

### Provider-outage replay exception and incarnation boundary

The general authoritative Admin requirement applies to every **new** prepare, observation, grant and conflict completion. It does not apply to recovery of an already committed result: current verified Google token, matching app/environment/UID, live-account guard, operation fingerprint/ownership, and required proof/destination binding suffice before returning stored receipts/completion. Conflict replay verifies the stored proof hash and bound destination, but does not require fresh recent-auth, Admin, Integrity or policy calls. This exception is necessary for honest retry semantics during provider outages.

Normal `DELETE /v1/me` erases/revokes operations, activations, grants and capabilities before Firebase removal; replay cannot restore them. Fresh uncommitted work compares authoritative Firebase creation/incarnation. A privileged **out-of-band Firebase deletion followed by reuse of the same UID while stale backend state survives** cannot be detected from ordinary token claims alone without a fresh provider call. That operation is outside the committed-replay incarnation guarantee and requires coordinated backend lifecycle invalidation/reconciliation. Do not claim both lookup-free outage replay and detection of that unobservable administrative replacement. This narrows the earlier incarnation wording: authoritative mismatch rejection is mandatory for new work, not an impossible prerequisite on every committed replay.

Required cases: direct new +2/+5 and recent brief anonymous phase; pre-cutoff/out-of-window rejection; combined requested actions/revision pair binding; signup-only challenge cannot acquire base; unchanged guest vectors; base unavailable/bonus available gives +5; bonus absent/paused/exhausted/base available gives +2; shared classification unavailable gives neither; distinct nullable revision binding; same-key partial snapshot replay after availability changes; explicit new-key base retry with signup paused; symmetric new-key +5 after base-first while base is paused/changed; no repeated prior grant or restored spending; continuity mutation rejected after first base attempt; both existing grants reconcile without providers; Admin outage committed replay; changed incarnation denied on uncommitted work; normal erasure revokes replay; documented out-of-band replacement limitation.
