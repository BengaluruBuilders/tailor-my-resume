## Chosen attachment protocol

Preserve the original automatic journey. A LINK candidate is automatically submitted after the user completes a qualifying Google continuation, without requiring the manual code-entry Apply action. Manual candidates continue to require Apply. Neither attribution source proves eligibility; both use the existing challenge and singular authenticated attach endpoint with identical atomic grant rules.

Permit fresh evidence only inside a bounded foreground referral operation, triggered by either (a) a newly delivered, strictly parsed external referral VIEW link or (b) the user's Google continuation while a LINK candidate is visibly disclosed on the existing sign-in surface. Show the candidate, current server offer and a Clear option using existing inline UI. This is feature disclosure, not a new consent/onboarding screen. For an already-Google actor opening a link, route to the existing referral surface, obtain and visibly render the current offer, then automatically run that foreground operation if eligible. Do not add an unconditional second Apply step. A VIEW event is untrusted input and is not cryptographic proof of a user gesture; all server qualification/security checks remain mandatory.

The fresh cold-start VIEW event must survive asynchronous Firebase initialization and normal navigation waiting in the current process. Resolve actual auth ownership, then bind it and show current referral state before protected work. An already-signed-in eligible recipient opening a cold link therefore works. Bare launcher startup, Firebase/auth restoration, policy/wallet/status refresh, install-referrer callback, background lifecycle callback and recreation of a previous intent are not fresh referral actions. Activity recreation must not redeliver its original intent as a new action. A resumed activity is necessary for evidence collection but resume alone never authorizes it.

Keep the foreground action permission ephemeral and single-use. Persist candidate and business attempt, not permission to collect evidence on a future launch. If the process dies or the operation is abandoned before evidence/send, retain the candidate and offer an inline Continue/retry when the user returns. If send may have occurred, use GET-first recovery below. This preserves automatic submission in the normal Google/link journey and explicitly handles interrupted journeys without passive evidence collection.

Before the first mutation: finish/reconcile the existing Google activation operation, refresh authenticated GET `/referrals/me`, stop on ATTACHED, require current ELIGIBLE status and usable offer, render its version/amount/deadline, and durably bind environment, UID/provider/session generation, canonical code, source LINK, request ID and revision. A successful signup bonus is not required: established Google activation and referral eligibility are. Do not manufacture a new activation/window from a link or successful Firebase sign-in. New link/Google events never bypass existing in-flight attempts or retry deadlines.

Use one serialization boundary for candidate capture and attachment. Create one business request ID per attempt; persist it before challenge/evidence/send. Preserve source and continuity payload across retries. Use the same existing challenge hash/action scope and strict Integrity verifier for LINK as MANUAL. No URL field supplies amount, inviter, API host, app ID, policy revision, eligibility or evidence. Current Android's null continuity remains sufficient for NONE and OPTIONAL modes; do not expand Android-ID collection in this slice.

POLICY_CHANGED or an observed revision change after display stops automatic submission. Refresh, show the changed offer, and require explicit inline reconfirmation before a fresh challenge for the same uncommitted business input/key. Missing/expired/paused/exhausted policy retains the candidate with neutral copy and normal app access; it does not start periodic automatic retries. Honor Retry-After. Evidence/provider unavailability is retryable failure, not approval or permanent fraud. A fresh user Retry may refresh evidence for the same attempt; neither key rotation nor new link delivery evades admission rules.

On uncertain response/process restoration, authenticated own GET comes first. ATTACHED clears code/key/digest/evidence/retry state and confirms only this account's receipt, not which local code won. If NOT_ATTACHED and an original attempt exists, recover with its original key/input before fresh evidence; a recovery-only path cannot collect Integrity. If further evidence is required, pause for a new foreground user Retry. Preserve slice03 detached-receipt, ALREADY_ATTACHED/read-only reconciliation and contradictory-GET handling. No automatic spending or tailoring follows any result.

## Candidate ownership and retention

- Retain the first syntactically valid candidate across LINK/referrer/manual capture. Store its canonical code and original source; later capture of the same code must not relabel it. Another link/referrer cannot replace it. Only explicit Replace/Clear can change it, and a new changed-code/source attempt receives a new business key. A first MANUAL candidate does not become automatically applicable when a later link repeats its code.
- Before Firebase initialization resolves a UID, keep one private environment-scoped pre-auth candidate, separate from account files. Do not assign it to an empty UID or whichever account happens to emit first from an unresolved auth stream. After initialization settles, bind a fresh launch link to that actual current actor; if no actor exists, bind through the subsequent deliberate guest/direct-Google entry. The same process's pending event may wait for this resolution. A restored pre-auth file alone confers no automatic evidence permission.
- A candidate owned by a guest follows its proven same-UID Google link. A cross-UID existing-Google credential conflict quarantines it through the existing review journal. Never auto-inherit it into the destination. An eligible destination can explicitly review/rebind it; preserve any existing destination candidate and require explicit replacement. A failed/cancelled upgrade leaves the original owner's candidate intact. Never transfer work or wallets because of a referral.
- Account switch/sign-out/deletion cancels work, clears account-bound/pre-auth candidates and attempts, and rejects late callbacks/responses using existing environment/UID/provider/generation/erase fences. A delayed referrer callback cannot repopulate a new account after a clear. Preserve any minimal installation-consumed marker separately, without a code, UID or digest.
- Do not invent a candidate TTL or confuse Play's referrer availability with eligibility. Candidate survives until attachment, explicit dismissal/replacement or owner cleanup. Server activation/deadline is authoritative. Do not store raw referrer URL, Integrity token/challenge secret or Android ID in this journal or logs.

## Strict link and Play handoff

Freeze `https://<configured-origin>/r/<canonical-code>` as the only link grammar. Maximum complete input 512 ASCII characters; code retains section 10 syntax/bounds. Origin is an exact lower-case ASCII DNS HTTPS origin, no wildcard, userinfo, port, path, query or fragment. Android compares the configured host exactly, never suffix-matches it. Reject query/fragment, extra/trailing path segments, dot segments, backslash, control/Unicode characters and percent escapes in this code path. Canonical code characters need no percent encoding, so accepting encoded path alternatives brings no benefit. Uppercase ASCII code can normalize through the existing code parser; generated links are canonical lower-case. No arbitrary deep links, custom schemes or redirects.

Play target is fixed `https://play.google.com/store/apps/details`, with exact configured application package `id` and one outer URL-encoded `referrer` value. The inner value is exactly `tmr_referral=<canonical-code>`; Play returns that inner string. Encode the outer referrer value once when constructing the store URL; Android parses the returned inner value without an additional whole-string percent decode. Require a single exact inner key/value, at most 1024 ASCII characters, and reject duplicate/unknown parameters, percent escapes, nested URLs and malformed input. No caller can override package, store origin or destination. LINK covers both App Link and Play transport; transport is local provenance, not a new rewarded source.

Use the explicitly planned official Install Referrer library behind an injected adapter; its dependency/version/baseline rationale belongs to the frontend PR. Read on first foreground execution after installation and close the service connection in every path. Durably mark terminal success/no-data/malformed/unsupported results consumed even when an existing candidate wins. Mark capture and consumption atomically so a crash cannot replay into another owner. A transient service failure permits a bounded retry on a later deliberate foreground entry, never a background poll; manual entry remains immediately usable. Sign-out, dismissal and attachment prevent replay of that installation's old result. The marker survives account cleanup and contains no identifying attribution data. Reinstallation may yield referrer data again, but cannot reset server account eligibility or grant uniqueness.

## Configuration, static ownership and truthful copy

Backend writer owns optional per-app/environment link configuration, link assembly, the separately hosted static landing template, public offer artifact generator, assetlinks generator, packaging instructions and tests in the backend repository. Frontend writer owns manifest/build configuration, parsing, referrer adapter, dispatch/journal/UI/share behavior. The single contract writer freezes their schemas/fixtures. Do not create two separately maintained landing implementations or a new hosting service/dependency.

Default is disabled: absent config yields `shareUrl:null`, no enabled referral intent filter or link/referrer capture, and code/manual flow remains operational. Existing nullable shareUrl communicates whether a concrete link can be shared; no new response capability field is required. A configured enabled capability requires an approved exact origin, `/r/` path, fixed package matching that environment, association fingerprint inputs, and landing publication configuration. Partial/invalid enabled configuration fails validation. Backend returns URLs from its configuration only; Android also rejects a share URL outside its build's approved origin/path before sharing. Staging and production origins/associations must be separate. No invented owned domain, API-origin fallback, public-domain assumption, fake certificate or live activation. Isolated tests may inject `.invalid` fixture origins explicitly labelled nondeployed; they are not shipped enabled associations.

The backend packager generates a public, nonpersonal offer snapshot from the same reviewed server referral policy publication input/revision used for the app offer. Include only app/environment, version, effectiveAt, expiresAt, published availability and optional reward amount. No user status, identifiers, counters, secret thresholds or credentials. All `/v1` routes remain authenticated; the public static site never queries private referral data or adds a public API resolver.

Landing reads its same-origin static snapshot, renders numeric conditional copy only inside its valid interval and for enabled admissions, and re-evaluates expiry while open. Missing/invalid/not-yet-effective/expired/disabled snapshots use neutral copy: “Open TailorMyResume to check the current referral offer.” Display/copy the safe code and fixed open/install links in either state. Render public text as text, never HTML from the code. No trackers, third-party scripts, arbitrary redirect or private inviter information. Package cache/referrer/security header requirements with the artifact; avoid leaking code to unrelated origins (`Referrer-Policy: no-referrer`).

Numeric copy is a published conditional offer, not real-time capacity or invitee eligibility: “An eligible referral may earn the inviter {amount} credits. Check availability in the app.” Android share text uses a freshly fetched usable server offer, its amount/version and conditional language; unavailable or unrefreshable offers use neutral link/code copy. Never embed amount/version into the referral URL as an entitlement. In-app automatic attachment always shows/rechecks the current authenticated offer; policy changes require reconfirmation as above.

Static hosting cannot establish instantaneous campaign capacity. This is an explicit limit, not permission to claim live availability. The publication runbook must couple policy changes to public snapshot replacement/invalidation, bounded expiry and cache control, and retain a neutral artifact fallback. Publish neutral first for a revision change, invalidate caches, apply the reviewed server policy, then publish the matching valid snapshot; do not publish a new numeric snapshot before that policy is active. Ordinary planned changes must respect the prior snapshot validity/cache bound; an emergency pause publishes neutral immediately and server admission still closes independently. If that operational coupling cannot be provided, deploy neutral landing copy only and leave quantitative/current public-offer activation BLOCKED. Code for both valid-snapshot and neutral paths still ships; neutral alone does not prove the original dynamic landing-copy acceptance gate. No Android release is needed to change the policy amount or public snapshot.
